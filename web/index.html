How long does a browser wait on a broken IPv6 path?

Happy Eyeballs is the rule that stops a dead or slow IPv6 route from stalling your connection. We built an isolated two-stack lab, broke one address family at a time, and measured what real clients actually do — from the packets, not from the client's own log.

The algorithm

What Happy Eyeballs does

A dual-stack host has two ways to reach the same server. If it tries only one and that one is broken, the user waits for a TCP timeout — often tens of seconds. Happy Eyeballs says: prefer IPv6, but do not wait forever.

Prefer IPv6

The client gets both records and orders IPv6 first. curl does this through glibc with the lab namespace's default address-selection rules; Chromium uses its own built-in DNS client, whose log shows IPv6 ordered first in all 140 of its runs.

Start a timer

Rather than waiting for a TCP timeout, the client gives IPv6 a short head start and then opens an IPv4 connection alongside it.

Take the first answer

Whichever handshake completes first carries the request. The other attempt is abandoned, and the user never sees the failure.

RFC 8305 describes this design. We cite it as a reference for the mechanism, not as a predictor of the exact timings any particular client uses — which is the thing this project set out to measure.

Our work

What we built

A measurement harness that can state a number and then prove it. Four pieces, all reproducible from the repository.

Lab

An isolated two-stack network

Linux network namespaces give a client and a server their own IPv4 and IPv6 addresses, plus a separate control link for DNS that is never impaired. Nothing touches the host's own networking.

Impairment

Faults we can switch on and off

Blackholes are enforced with static neighbour entries and verified at 100% loss with no ICMP errors. Latency is applied with netem on the server side in both directions, so the client's own capture stays truthful.

Harness

A runner that refuses to guess

Each run applies a scenario, verifies it, captures packets, runs the client, restores the baseline, verifies again, then parses the capture. It stops on a failed check and restores the lab on any error or interrupt.

Evidence

Every value carries its status

Results are stored as a value with a status rather than a bare number, alongside a cross-check block. Where the client's log and the packet capture disagree, the run is flagged instead of quietly resolved.

Method

How the lab is built and why it can be trusted

The measurement is only as good as the thing being measured. This page sets out the topology, the fault model, the exact definition of every metric, and the checks that have to pass before a run counts.

Topology

Why the impairment sits on the server side

Client-side netem shapes packets after tcpdump has already seen them, so the capture records a send time that never happened and drops disappear entirely. We apply netem to the server's egress for the server-to-client direction, and redirect the client-to-server direction through an IFB device inside the server namespace carrying the same rule. The client's interfaces carry no qdisc at all, so its capture shows true send and receive times.

Added RTT stacks on a 20 ms baseline (10 ms each way), so “+600 ms” means a 620 ms target round-trip time and “+150 ms” means 170 ms. The real round-trip time is measured before every scenario rather than assumed. S2, S3 and S5 are mobile-inspired latency conditions.

Metrics

metric 1

TCP setup time

From the first SYN of the run to the ACK that completes the winning handshake. DNS is deliberately excluded, so a delayed record does not inflate it.

metric 2

Inter-family attempt delay

The second family's first SYN minus the first family's first SYN. Recorded as not_observed when only one family was ever tried.

metric 3

Scenario penalty

A client's median setup time in a scenario minus its own median in the healthy control. Computed across runs, never per run, so each client is its own baseline.

What has to pass before a run counts

Cross-checks

Every record carries a cross-check block covering six checks: the client's success claim against the capture, the HTTP status, the address the client says it used against the destination of the winning handshake, whether the capture was ambiguous, any port-443, QUIC or other-port traffic, and whether tcpdump dropped or failed to write any packet. A dropped or unwritten packet is recorded as a capture conflict and stops the session. Any disagreement flags the run and exits with an error rather than being resolved silently.

Fault verification

A blackhole is only accepted at 100% loss with zero ICMP errors, using static neighbour entries so no address resolution is needed. Latency targets are measured before each scenario, and the lab is restored and re-verified after every run.

Pinned fixtures

Two small captures are stored as test fixtures with pinned checksums, listed on the Evidence page. The parser tests must keep reproducing their known values before any change is accepted.

Known limits

Where the parser had to define a rule that the metric description leaves open — what counts as abandoned, where DNS time ends — the rule is written down and marked for sign-off rather than buried in the code.

Reproducing a run

sudo ./scripts/setup.sh # build both namespaces and the links
./scripts/verify.sh # assert addresses, routes and RTTs
python -m src.runner.orchestrate \
--scenario S1 --client curl --reps 20 # apply, capture, run, restore, parse
sudo ./scripts/teardown.sh # leave the host exactly as it was

Each run writes a packet capture and a JSON record. Files created under sudo are handed back to the operator automatically.

What this model assumes
  • Baseline 20 ms round-trip time; added latency stacks on top.
  • Resolution takes 4 ms plus any record delay, and the client waits for both answers.
  • Setup time runs from the first SYN to the completing ACK and excludes DNS.
  • The fallback timer and Chromium's backup attempt are model settings, not measurements. In the dataset's S1 and S2 runs, curl started IPv4 a median 201 ms after its first IPv6 SYN; Chromium sent a second IPv6 attempt at a median 251 ms and started IPv4 at 301 ms.
