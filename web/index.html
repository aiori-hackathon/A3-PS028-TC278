The problem

How long does a browser wait on a broken IPv6 path?

As IPv6 deployment grows, dual-stack hosts must connect over both address families. When one path is broken — a black-holed route, unreachable next-hop, or slow DNS — a naive client that tries only one address family forces the user to wait out a full TCP connect timeout — on Linux, around 130 seconds with default SYN retries. Happy Eyeballs (RFC 8305) removes that wait by racing both families and taking whichever completes first.

We built an isolated dual-stack lab, broke one address family at a time under seven controlled conditions, and measured what real clients actually do — from the packets on the wire, not from the client's own log.

RFC 8305 · Happy Eyeballs Version 2

What Happy Eyeballs does

A dual-stack host resolves a hostname to both A (IPv4) and AAAA (IPv6) records. Without Happy Eyeballs, if the preferred family is unreachable, the connection stalls until TCP times out — often tens of seconds. RFC 8305 defines a connection-racing algorithm that eliminates this penalty.

The algorithm runs in three phases, and RFC 8305 names a timer for two of them. The client sends the A and AAAA queries together; if the A answer comes back first it waits a short Resolution Delay — recommended 50 ms — to give the AAAA answer a chance before committing to IPv4. It then sorts the addresses with IPv6 preferred and opens a TCP connection to the first one. If that handshake has not completed within the Connection Attempt Delay — recommended 250 ms, with a floor of 100 ms and a ceiling of 2 seconds — it opens a parallel attempt to the first address of the other family, and further attempts follow at the same stagger until one succeeds.

1. Prefer IPv6

The client resolves both A and AAAA records and interleaves them with IPv6 first, following the address-sorting rules of RFC 6724. This gives IPv6 priority without betting the whole connection on it.

2. Connection Attempt Delay

RFC 8305 recommends 250 ms before starting a fallback attempt. If the first SYN has drawn no SYN-ACK within that window, the client opens a second connection to the other address family in parallel. curl's own default is 200 ms, which is what we measure here.

3. First handshake wins

Whichever TCP three-way handshake completes first carries the application data. All other in-flight attempts are cancelled. The user never sees the failed path — the penalty is just the fallback delay, not a full timeout.

RFC 8305 ("Happy Eyeballs Version 2: Better Connectivity Using Concurrency," D. Schinazi and T. Pauly, December 2017) defines this mechanism. The original Happy Eyeballs algorithm was specified in RFC 6555 (2012). Our lab measures how closely real clients — curl and Chromium — follow this design under controlled fault conditions.

System Architecture / How every measurement is made

Inside the measurement engine

Every number on this site comes from a fully automated pipeline that sets up isolated network namespaces, injects precise faults, captures packets, runs the client, parses timestamps from the wire, and cross-checks every result.

setup.sh→ verify.sh→ orchestrate.py→ teardown.sh→ summarise.py→ export_web.py
Network isolation Linux netns

The lab runs inside two Linux network namespaces on one machine: no VMs, no containers, no external hosts. Names and addresses come from one file, src/lab/lab.env.

hl-client curl / Chromium (via Playwright), tcpdump ├─ hl-v6c 2001:db8:28:6::1/64 (IPv6 link, impaired by scenarios) ├─ hl-v4c 192.0.2.1/24 (IPv4 link, impaired by scenarios) └─ hl-ctlc 198.51.100.1/24 (control link for DNS, never impaired) hl-server nginx :80, DNS responder :53 ├─ hl-v6s 2001:db8:28:6::2/64 + hl-ifb6 ├─ hl-v4s 192.0.2.2/24 + hl-ifb4 └─ hl-ctls 198.51.100.53/24

setup.sh

Creates both namespaces and the three veth pairs, assigns addresses, adds default routes in hl-client (Chromium checks for an IPv6 route to a global address) and static nud permanent neighbour entries on the v4 and v6 links. It creates hl-ifb4/hl-ifb6 inside hl-server and redirects each server end's ingress to its ifb, then sets the 20 ms baseline RTT: 10 ms each way, as netem on the server end (server to client) and on its ifb (client to server). It writes the lab-only resolv.conf and gai.conf under /etc/netns/hl-client/, then runs verify.sh up 20 20, which measures the real RTT. nginx and the DNS responder are started by the orchestrator, not by setup.sh.

teardown.sh

Deletes both namespaces, which removes their veths, qdiscs, routes and neighbour entries, and removes the lab-only resolver files. It then runs verify.sh down, which confirms no hl- namespace or interface is left on the host.

DNS responder dnslib · Python

src/dns/hl_dns.py is a small authoritative server built on Python's dnslib, listening on UDP at 198.51.100.53 on the control link, outside the impaired data path. It serves one name with TTL 0:

www.hl.test A 192.0.2.2 ← IPv4 server address AAAA 2001:db8:28:6::2 ← IPv6 server address

How it works

  • answer(data, zone) builds the reply to one query. An A query gets the A record and an AAAA query gets the AAAA record, each in its own response. Other names under hl.test get NXDOMAIN; names outside it are refused.
  • A per-type delay is set on the command line, e.g. --delay AAAA=300 for S6. The AAAA reply is held for 300 ms while the A reply goes out at once.
  • The client finds it through /etc/netns/hl-client/resolv.conf, which ip netns exec mounts as /etc/resolv.conf inside hl-client only.

Chromium resolves with its own built-in DNS client rather than glibc, but it reads the same resolv.conf and queries the same server. Its NetLog showed IPv6 ordered first in 140 of 140 runs.

Impairment engine netem · IFB

Every impairment is applied on the server side, so the client interfaces, where tcpdump captures, carry no qdisc. A netem qdisc on the client's own egress would act before tcpdump sees the packet, hiding dropped SYNs and timestamping delayed ones late.

Latency injection

# S2: +600 ms on IPv6 → 620 ms target RTT = 310 ms each way src/lab/netem.sh v6 310 0 # family, delay each way (ms), loss % # which runs, inside hl-server: tc -n hl-server qdisc replace dev hl-v6s root netem delay 310ms # server → client tc -n hl-server qdisc replace dev hl-ifb6 root netem delay 310ms # client → server

Linux can't delay ingress traffic directly, so the server end's ingress is redirected to an ifb (Intermediate Functional Block) device, and netem shapes it there as egress.

Blackhole injection

# S1: IPv6 blackhole, 100% loss in both directions on the v6 link src/lab/netem.sh v6 10 100 tc -n hl-server qdisc replace dev hl-v6s root netem delay 10ms loss 100% tc -n hl-server qdisc replace dev hl-ifb6 root netem delay 10ms loss 100%

The client's SYN leaves hl-client and appears in the capture, then is dropped on the server's ingress, so no SYN-ACK ever comes back. The static nud permanent neighbour entries matter here: without them the loss would also stop ARP/ND, and the client would see "host unreachable" errors instead of a silent drop. verify.sh confirms the drop before each run.

Orchestrator orchestrate.py

The controller that drives every measurement. It is run with sudo (never sudo -E, which would pass the shell's ROS variables through), and run_matrix.py calls it once per client and scenario:

.venv/bin/python src/runner/orchestrate.py --client curl --scenario S1 --reps 20

One run: run_one()

  1. Apply the scenario: netem.sh for v4 and for v6, with the delay and loss from src/config/scenarios.yaml.
  2. Pre-run verify: verify.sh up <v4 target> <v6 target> measures the real RTT, or confirms 100% loss on a blackholed family.
  3. start_capture(): tcpdump in hl-client (-i any --immediate-mode), writing captures/<run_id>.pcap, where run_id is <UTC time>_<scenario>_<client>_r<NN>.
  4. Run the client inside hl-client as the normal user, with ROS variables stripped from its environment: curl -q -sS --noproxy '*' --max-time 10 -o /dev/null -w '…' http://www.hl.test/, or Chromium via Playwright loading http://www.hl.test/chromium.html.
  5. stop_capture(): stops tcpdump and reads its dropped and written packet counts.
  6. restore_baseline(): netem.sh back to 10 ms each way, no loss, on both families.
  7. Post-run verify: verify.sh up 20 20.
  8. parse() from parse_pcap.py reads this run's time window from the pcap; build_record() computes the metrics and cross-checks, and the record is validated against the schema before it is written.

The orchestrator doesn't retry. If a verify fails, it restores the baseline and stops the session, and an incomplete capture stops it too. Every run in the 280-run dataset records pre_verify_ok and post_restore_verify_ok as true.

Pcap parser struct · dnslib

After each run, src/analysis/parse_pcap.py reads the capture with its own small pcap reader (Python struct, no scapy or libpcap). It decodes Linux "cooked" (SLL2) frames, IPv4/IPv6, TCP and UDP, and uses dnslib only to decode DNS messages.

What it extracts

linktype, packets = read_pcap(path) # every frame, ns timestamps timeline = analyse(linktype, packets, window) _track_tcp() # one Attempt per connection: first SYN, retransmits, # SYN-ACK, RST, completing ACK (timestamps only) _track_dns() # pairs each query with its answer, per record type

Computed metrics (metrics.py)

metrics.py decides which attempt won and labels the others abandoned, failed or no_reply, then computes:

  • tcp_setup_time_ms: from the run's first SYN (of either family) to the ACK completing the winning handshake. DNS time is not included.
  • inter_family_attempt_delay_ms: the second family's first SYN minus the first family's first SYN. It is not_observed when only one family was tried.
  • dns_time_ms: from the first DNS query to the last answer, so S6's held AAAA answer shows up here.
  • winning_family: the family whose handshake completed, v6 or v4.

Every timestamp is the capture's own packet timestamp (microsecond resolution), not the client's report.

Run record schema v0.2 {value, status}

Every metric is stored as a {value, status} pair — the number alone is not enough. The status field records how the number was obtained.

{ "schema_version": "0.2", "run_id": "20261026T193106Z_S1_curl_r08", "scenario": { "id": "S1", "repetition": 8 }, "client": { "name": "curl" }, "metrics": { "tcp_setup_time_ms": { "value": 222.254, "status": "computed" }, "inter_family_attempt_delay_ms": { "value": 200.976, "status": "computed" }, "dns_time_ms": { "value": 1.069, "status": "computed" } }, "outcome": { "success": true, "http_status": 200 }, "cross_checks": { "status": "agree", "conflicts": [] } }

Status values

  • computed: derived from the capture
  • not_observed: the event did not appear in the capture (for example, no second family tried, so no inter-family delay)
  • not_applicable: the field has no per-run value (the scenario penalty is a per-scenario aggregate)

Cross-checks block

Each record compares the client's own report with the capture, field by field: winning family, success, HTTP status, the client's connected address against the winning handshake's destination, unexpected traffic (port 443, QUIC or other ports), and capture completeness (tcpdump dropped or failed to write no packet). Any disagreement is stored as a conflict with both values, and a capture conflict stops the session. Across 280 runs: 0 conflicts.

Chromium runner Playwright

Chromium doesn't use glibc's getaddrinfo or the lab's gai.conf here. It has its own built-in DNS client and its own connection logic, which is why it is measured separately from curl.

How it runs (client_chromium.py)

browser = p.chromium.launch( channel="chromium", headless=True, # full Chromium, new headless mode chromium_sandbox=False, args=["--disable-quic", "--disable-features=<Playwright's list>,DnsOverHttps", "--log-net-log=<run_id>_netlog.json", "--net-log-capture-mode=Default"], ignore_default_args=[<Playwright's own --disable-features>]) page.goto("http://www.hl.test/chromium.html", wait_until="load", timeout=15000)

Chromium honours only one --disable-features switch, so the runner merges its own entries into Playwright's list instead of adding a second one. QUIC, Secure DNS and HTTPS-Upgrades are off. After each run it reads the browser's command line back from the NetLog and fails the run if those settings are missing.

Key difference from curl

The captures show Chromium opening a second IPv6 attempt at around 250 ms before it tries IPv4 at all, so each S1 run has two abandoned IPv6 attempts against curl's one. Its median fallback to IPv4 lands at 301.067 ms against curl's 200.956 ms, so Chromium reaches the working path about 100 ms later under a blackhole. We report the timings we measured and don't infer the internal timer that produces them.

Data pipeline summarise → export

Two scripts turn 280 individual run records into the figures on this site.

summarise.py

  • Reads only the 14 sessions listed in docs/dataset.md from data/generated/runs/
  • Groups by (scenario, client) and computes median TCP setup time, inter-family delay, winner counts and the scenario penalty against the client's own C0
  • Stops with an error on any cross-check conflict, failed verify or missing run
  • Writes data/generated/summary/summary.json and runs.json; dashboard.py builds the Plotly dashboard from the same loader

export_web.py

  • Reads the same 14 sessions' run records directly, using summarise.py's loader, and leaves out any run with a conflict or a failed verify, naming it
  • Rewrites only the JavaScript data objects (D, WIN, IFDV, RUNS, CAPS) between the generated-data markers in this static page
  • Every inter-family dot on the charts is a real per-run value with its run ID: no jitter, no synthetic points
  • The repository has 285 automated tests; 20 of them cover export_web.py

Our work

What we built

A measurement harness that can state a number and then prove it.

Lab

An isolated two-stack network

Linux network namespaces give a client and a server their own IPv4 and IPv6 addresses, plus a separate control link for DNS that is never impaired.

Impairment

Faults we can switch on and off

Blackholes are 100% netem loss on the server side, kept a silent drop by static neighbour entries, and verified before every run. Latency is applied with netem on the server side, in both directions.

Harness

A runner that refuses to guess

Each run applies a scenario, verifies it, captures packets, runs the client, restores the baseline, verifies again, then parses the capture.

Evidence

Results are stored as a value with a status rather than a bare number, alongside a cross-check block.

Method

How the lab is built and why it can be trusted

The measurement is only as good as the thing being measured. This page sets out the topology, the fault model, the exact definition of every metric, and the checks that have to pass before a run counts.

Topology

Why the impairment sits on the server side

Client-side netem shapes packets after tcpdump has already seen them, so the capture records a send time that never happened. We apply netem to the server's egress for the server-to-client direction, and redirect the client-to-server direction through an IFB device.

Conditions

IDIPv6 pathIPv4 pathDNSWhat it answers

Added RTT stacks on a 20 ms baseline (10 ms each way). S2, S3 and S5 are mobile-inspired latency conditions.

Metrics

metric 1

TCP setup time

From the first SYN to the ACK that completes the winning handshake. DNS is deliberately excluded.

metric 2

Inter-family attempt delay

The second family's first SYN minus the first family's first SYN. Recorded as not_observed when only one family was tried.

metric 3

Scenario penalty

A client's median setup time in a scenario minus its own median in the healthy control.

What has to pass before a run counts

Cross-checks

Every record carries a cross-check block covering six checks: the client's success claim, HTTP status, address used, capture ambiguity, unexpected traffic, and capture completeness. Any disagreement flags the run.

Fault verification

A blackhole is only accepted at 100% loss with zero ICMP errors. Latency targets are measured before each scenario, and the lab is restored and re-verified after every run.

Pinned fixtures

Two small captures are stored as test fixtures with pinned checksums. The parser tests must keep reproducing their known values.

Known limits

Where the parser had to define a rule that the metric description leaves open, the rule is written down and marked for sign-off.
